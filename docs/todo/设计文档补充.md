RFC 在架构层面定义了五组件的职责边界和交互关系，但到可实现的代码层面，还差七个设计文档。下面逐个说清楚每份文档的范围、要展开的核心论点，以及最该认真写的备选方案。

---

### 一、OGAS-Dispatcher Fork 详细设计

**范围。** 这份文档要回答的核心问题是：fork Multica 之后，四层改动（liskin runtime 注册、状态事件引出、ask 双向通道、API facade）各自的接口契约、数据流和实现策略是什么。

**要展开的点。**

第一层 liskin provider 的设计需要定义 Daemon 与 `liskin agent exec` 进程之间的通信契约。stdin 写入的提示词格式是什么——纯文本还是结构化 JSON？stdout 返回的结构化结果 schema 长什么样？进程退出码与 Dispatcher 状态机的映射关系（0 → Completed，非 0 → Failed，超时 → 重试还是直接 Failed）。MVP 阶段的薄 shim 怎么写——是直接把 liskin 包装成 Multica 已支持的某个 provider 的接口形态，还是自己注册一个新的 provider 类型？这两条路的取舍需要在文档里讲清楚。

第二层状态事件引出，要定义事件 schema：事件类型（Completed / Failed / 重试耗尽 / Cancelled）、payload 结构、推送方式（WebSocket 还是单独的事件总线）。"重试耗尽"与普通 Failed 的区分语义怎么落——是两个不同的事件类型，还是同一个类型加一个 `retry_exhausted: true` 字段？Flow 消费时怎么区分？

第三层 ask 双向通道是这份文档里最值得认真写的部分。它要在 WebSocket 上开一个子协议，把 liskin 的 Sandbox ask 提示从 Daemon 一路串到飞书群，再把人的确认回灌进 liskin 进程的 stdin。需要定义：ask 消息的 schema、确认/拒绝的回灌格式、超时策略（人在群里多久不确认就算自动拒绝？）、以及确认动作跳转到强身份校验界面后的回调机制。这里的关键权衡是：复用 WebSocket 连接还是另开独立通道？复用省基础设施但混了控制流和数据流，另开干净但多一层运维。

第四层 API facade 要定义对外暴露的接口面：issue 的建/派/改状态/评论、任务状态流转的 WebSocket 订阅、活动时间线镜像。关键设计是版本化策略——facade 层怎么做版本管理，上游 Multica schema 变了怎么隔离影响。这份文档要给出 facade 的接口清单（不贴完整定义，但要让读者知道有哪些端点），以及 Gate/Flow 调用 facade 时的认证和权限模型。

**备选方案必须写的一段。** 完全自研控制面 vs fork Multica。RFC 在架构层已经选了 fork，但设计文档要补上更具体的论证：如果 Multica 的 NOASSERTION 许可证法务不放行，完全自研的工作量估算、排期影响、以及自研版需要从零实现哪些 Multica 已有的能力（workspace/issue/队列/权限/WebSocket hub/超时重试）。这个备选方案写扎实了，法务一关就能直接切。

### 二、OGAS-Flow 设计文档

**范围。** DAG 编排器的完整设计：数据结构、推进算法、事件消费、崩溃恢复、校验机制、库选型落地。

**要展开的点。**

DAG 定义格式的完整 schema 设计。RFC 给了一个 YAML 示例，但设计文档要定义完整的字段：节点 id 的命名规范、type 枚举（AGENT/GATE/JOIN）、AGENT 节点的 issue 模板引用方式、GATE 节点的判定表达式语法（是 CEL？是 JSONPath？还是自定义 DSL？）、JOIN 节点的汇聚语义（全完成才解锁，还是 N 选 M？）。判定表达式的语法选型是一个需要认真权衡的决策点——CEL 表达力强但有学习成本，JSONPath 简单但不够灵活，自定义 DSL 灵活但又要自己写解析器和校验器。

`next_ready` 纯函数的输入输出契约要精确定义。输入是 DAG 拓扑定义和已完成集合，输出是待派发节点列表。但"已完成集合"的数据结构是什么——一个 `Set<node_id>`？还是需要带时间戳和终态类型（Completed vs Failed）的富结构？如果某个节点 Failed 了，Flow 是直接阻断整条链路，还是走补偿分支？第一版 RFC 说"只做线性串联"，但设计文档要把失败语义定义清楚：AGENT 节点 Failed 后，下游节点的状态是什么——Blocked？Cancelled？还是也标成 Failed？

事件消费与 Dispatcher 的对接。Flow 订阅 Dispatcher 的哪些事件、通过什么协议订阅（WebSocket 还是 webhook 回调还是轮询 Postgres）、消费幂等怎么保证（事件 ID 去重？）。RFC 说"别让 Flow 去轮询"，但设计文档要给出具体的订阅机制。

崩溃恢复的工程实现。RFC 说了事件溯源的思路，设计文档要落到可实现的层面：事件流存在哪里（复用 Dispatcher 的 Postgres，建一张专门的 `flow_events` 表？）、重放的起点怎么确定（从头重放还是从某个 checkpoint 开始）、重放过程中如果有新事件到达怎么办（加锁？CAS？）。

Dry-run 模拟器的设计。模拟器怎么 mock 掉 liskin——是 mock 在 Dispatcher 层（让 Dispatcher 返回合成终态）还是 mock 在 Flow 层（直接给 Flow 喂合成事件）？OrchBench 六个维度的校验规则怎么落地成具体的断言。

**备选方案。** 第一版的"纯 DAG 库 + Postgres + 纯函数"组合 vs 直接上 Temporal。RFC 已经选了前者，但设计文档要论证：在 MVP 的线性串联场景下，Temporal 的额外运维成本（需要部署 Temporal Server、学习 workflow/activity 编程模型）是否值得？以及在什么信号下触发升级——是"需要条件分支"就升级，还是要等到"自动补偿回滚"才升级？升级路径怎么走——是 Flow 整体替换成 Temporal workflow，还是把部分节点迁移过去？

### 三、OGAS-Gate 设计文档

**范围。** 飞书机器人适配服务的完整设计：事件接收、指令解析、状态回流、ask 通道的 IM 侧落地。

**要展开的点。**

指令解析层的设计。群聊里的自然语言指令怎么翻译成 Dispatcher API 调用——是用规则匹配（正则 + 关键词）还是过一层 LLM 做意图识别？规则匹配快但脆弱，LLM 灵活但引入新的不确定性（Gate 本身不该调 LLM，但指令解析如果用 LLM 就违反了"编排层零推理"的精神——虽然 Gate 不是编排层）。这里的权衡需要明确：如果用 LLM 做指令解析，它属于 Gate 内部的实现细节，还是需要单独立一个轻量 NLU 服务？RFC 4.3 定义了"可在群内直接触发"和"必须跳转"两档操作，设计文档要把每档操作的交互流程画清楚——群内触发的消息格式、跳转时的 H5 审批页面的 URL 生成和回调机制。

状态回流的实现。Gate 订阅 Dispatcher 的 WebSocket 事件流，把状态流转翻译成飞书群消息。三种回流粒度（全量/终态/混合）的配置怎么存——在 Dispatcher 的 workspace 级别配置，还是 Gate 自己存？飞书消息的格式设计——是纯文本、富文本卡片，还是交互式卡片（带按钮的那种，比如"查看详情""取消任务"）？消息合并策略——短时间内同一个 task 的多次状态流转是各发一条还是合并成一条？

ask 通道的 IM 侧落地。高危操作的 ask 提示在飞书群里长什么样——是普通消息提醒还是卡片消息带交互按钮？跳转到强身份校验界面后，这个界面是飞书内嵌 H5 还是独立 Web 系统（RFC 7.4 待决问题）？设计文档需要给出推荐方案并说明理由。确认后的回调链路：H5 审批页 → Gate → Dispatcher Server → Daemon → liskin stdin，这条链路的每跳协议和超时策略要定义。

**备选方案。** 指令解析的两条路：规则匹配 vs LLM NLU。以及 Gate 的部署形态——独立服务 vs 作为 Dispatcher 的一个 plugin。独立服务解耦清晰但多一层运维，plugin 形态省部署但把 IM 适配逻辑塞进了控制面，可能违反"Dispatcher 不碰 IM 协议"的边界。

### 四、OGAS-Arkhiv 设计文档

**范围。** 基于 EagleRAG 的业务知识库改造：权限模型、命名空间设计、与 liskin 的 MCP 对接细节。

**要展开的点。**

权限模型设计。RFC 说"在 plugin_namespace 机制上叠加团队/workspace 级别的权限控制"，设计文档要落到具体：权限粒度是什么——workspace 级（整个团队共享一个知识库）还是 document 级（每篇文档可单独授权）？权限操作有哪些——read（检索）、write（ingest）、admin（管理命名空间）？权限怎么跟 Dispatcher 的 workspace 成员体系打通——是 Gate/Dispatcher 传 workspace_id 给 Arkhiv 做 ACL 校验，还是 Arkhiv 独立维护一套权限表？

命名空间设计。PRD、接口契约、UI 规范、历史决策这四类文档怎么组织成命名空间——按文档类型分（prd/、contracts/、ui-specs/、decisions/）还是按业务线分（product-a/、product-b/）再在下面按类型分？命名空间的层级深度限制。Agent 检索时怎么指定命名空间——是 liskin 在 prompt 里显式指定，还是 Arkhiv 根据当前 task 关联的 workspace 自动限定检索范围？

MCP Server 的接入配置。Arkhiv 作为 MCP Server 常驻，端点地址配在 Agent 级的 `custom_env` 里。设计文档要定义：Arkhiv 暴露哪些 MCP 工具（retrieve / query / ingest）、每个工具的参数 schema、以及 streamable HTTP 和 stdio 两种接入方式分别用在哪——Daemon 直接 spawn liskin 时用 stdio 接 Arkhiv，还是 liskin 通过 HTTP 远程调 Arkhiv？

**备选方案。** EagleRAG 改造 vs 自建知识库。如果 EagleRAG 的 plugin_namespace 机制改造成本比预期高（比如它假设的是单租户场景，多租户改造侵入核心），是否值得自建一个轻量的 MCP Server 包一层 Milvus？以及知识检索的备选：向量检索 vs 全文检索 vs 混合——代码场景下，精确的符号匹配可能比语义检索更管用。

### 五、liskin Runtime Provider 设计文档

**范围。** liskin 作为 Multica Daemon 的一个 runtime provider 的完整适配设计——这是 fork 改动的第一层，也是最核心的集成工作。

**要展开的点。**

Daemon 检测和注册 liskin runtime 的机制。Multica Daemon 启动时扫描 PATH 上的 AI CLI 工具，设计文档要定义：liskin 的检测规则是什么——检查 `liskin` 命令是否在 PATH 上？检查特定版本？注册成 runtime 时的 metadata schema（runtime name、version、支持的 capabilities）。

进程通信契约的完整定义。这是这份文档的核心。Daemon spawn `liskin agent exec` 后，stdin/stdout 的通信协议要精确定义。需要回答：提示词是单次写入还是流式写入？liskin 的执行进度怎么回传——stdout 是只返回最终结果，还是支持流式输出中间进度？如果支持流式，进度消息和最终结果消息怎么区分（用 JSON Lines 的 `type` 字段区分？）？进程信号处理——Daemon 收到取消信号时怎么传给 liskin（SIGTERM？liskin 有没有优雅退出的机制？Harness 框架的中断恢复怎么配合？）。

MCP 工具注入的透传设计。Arkhiv 端点、GitHub token、Vercel token 通过 `custom_env` 透传给 liskin 进程，设计文档要定义：环境变量的命名规范（`OGAS_ARKHIV_ENDPOINT`、`GITHUB_TOKEN`、`VERCEL_TOKEN`？）、liskin 启动时怎么发现和加载这些 MCP 配置——是 liskin 自己读环境变量初始化 MCP client，还是 Daemon 在 spawn 时传入一个 MCP 配置文件路径？

Harness 状态与 Dispatcher 状态的解耦边界。RFC 反复强调两层状态必须解耦，设计文档要落到可操作的层面：Daemon 调用 liskin 后，什么信号算"任务开始"（进程启动？liskin 输出第一条进度消息？）、什么信号算"任务完成"（进程退出码 0？stdout 输出结构化完成消息？）、什么信号算"任务失败"（进程非 0 退出？stdout 输出结构化失败消息？超时？）。Harness 框架的中断恢复是 liskin 内部的事，Daemon 完全不感知——但万一 Harness 恢复失败导致进程 hang 住怎么办？Daemon 的看门狗超时怎么设。

**备选方案。** 仿 pi adapter 写一个原生 liskin provider vs 用薄 shim 把 liskin 包装成已支持的 provider 形态。RFC 提到 MVP 可以先用 shim 过渡，设计文档要给出 shim 的具体实现方式——是写一个 wrapper 脚本把 liskin 的 stdin/stdout 格式转成 pi 的格式，还是直接在 Multica 的 provider 接口层做适配？以及从 shim 切到原生 provider 的迁移路径和时间点。

### 六、Vercel 集成设计文档

**范围。** Vercel Deployment Checks 发布门、回滚机制、以及这些在 OGAS-Flow GATE 节点里的落地。

**要展开的点。**

Webhook 集成的完整设计。Vercel 发出 `deployment.created` / `deployment.ready` / `deployment.succeeded` / `deployment.error` 这些 webhook，OGAS 这边谁接——是 Dispatcher 接，还是 Gate 接，还是单独开一个 webhook receiver 服务？接到后怎么触发 liskin 验证——是在 Dispatcher 里建一个临时 issue 派给 liskin，还是直接调 liskin exec？验证结果通过 Checks API 回写的接口契约——回写 success/failure 的 API 调用、超时策略（Vercel 的 Check 有默认超时，OGAS 的验证必须在超时前完成）。

GATE 节点的判定表达式设计。RFC 的 YAML 示例里 GATE 节点有 `check: "vercel_deployment_check"`，设计文档要定义这个 check 的完整语义：它是一个同步查询（查 Vercel API 看部署状态）还是一个异步等待（等 webhook 回来）？如果是异步等待，GATE 节点进入 waiting 状态后由什么事件唤醒？判定表达式的返回值——pass / fail / timeout，各自对应的下游行为是什么？

回滚流程的工程实现。`vercel rollback` 触发后，GATE 节点怎么知道回滚完成了——轮询 Vercel API 还是等 webhook？pinned 状态怎么检测和告警——Gate 定期查 deployment 状态发现被 pinned 了就在群里高亮？`vercel promote` 恢复自动部署的触发时机——是回滚后自动提醒人去 promote，还是作为另一个 GATE 节点串在 DAG 里？

MCP 工具层的设计。Vercel 以 MCP 接入 liskin，设计文档要定义：暴露哪些 MCP 工具（trigger_deploy / check_deployment_status / rollback / promote）、每个工具的参数和返回值 schema、以及权限控制——rollback 和 promote 是高危操作，在 MCP 工具层面怎么跟 liskin 的 Sandbox ask 档配合（工具被标记为 ask，liskin 调用时自动触发人工确认？）。

**备选方案。** Vercel Deployment Checks vs GitHub Actions 做 CI 门控。RFC 选了 Vercel Checks，设计文档要论证：GitHub Actions 在 PR 阶段就跑验证 vs Vercel Checks 在构建后跑验证，两者的拦截时机和覆盖面有什么差异？为什么选了后者——是因为 Vercel Checks 能在域名分配前卡住，而 GitHub Actions 做不到？以及如果 Vercel 的 Checks API 未来变了或者 Vercel 被换掉，这套设计的可迁移性。

### 七、端到端可观测性设计文档

**范围。** 这是一份横切关注点文档，覆盖从飞书消息到 Vercel 部署的完整链路的 tracing、结构化日志、监控告警。

**要展开的点。**

Trace ID 的生成和传递策略。RFC 5.3 说"每一层都应该在请求入口打上 trace ID，逐层传递"。设计文档要定义：trace ID 在哪里生成（Gate 收到飞书事件时？还是 Flow 派发 DAG 时？）、怎么跨进程传递（Gate → Dispatcher API 的 HTTP header？Dispatcher → Daemon 的 WebSocket 消息字段？Daemon → liskin 的环境变量或 stdin 的 metadata 字段？）。链路里有异步断点（DAG 节点之间等待下游解锁），trace 怎么跨断点续接——是用一个 DAG 实例 ID 串联所有节点，还是每个节点独立 trace 再用 parent span 关联？

结构化日志的 schema。每层组件的日志格式统一成什么——JSON 结构化日志？关键字段有哪些（trace_id、task_id、workspace_id、node_id、timestamp、level、message、component）？日志存哪里——各组件本地文件 + 统一日志收集，还是直接写 Dispatcher 的 Postgres？

监控指标和告警。关键 SLI 指标：任务派发延迟（Queued → Dispatched）、任务执行时长（Dispatched → Completed）、任务失败率、ask 通道响应时长（ask 发出到人确认回来）。GATE 节点的通过/失败率。Vercel 发布门的拦截率。告警策略：任务失败率突增、ask 通道超时、Dispatcher 状态机卡住（某个 task 长时间停在 Running）。

**备选方案。** 自建 trace 链路 vs 接入 OpenTelemetry。自建轻量但重复造轮子，接入 OTel 有生态但引入额外依赖。考虑到 OGAS 是自托管内部系统，团队可能已经有日志/trace 基础设施（比如内部的可观测平台），设计文档要评估复用已有基建的可行性。

### 横切关注点：安全与合规

这份不单独成文档，但应该作为一份独立的横切关注点文档，覆盖所有七个设计文档共通的安全议题：

**密钥管理。** GitHub token、Vercel token、Arkhiv 端点凭证通过 `custom_env` 透传给 liskin 进程，这些密钥存在哪里——Dispatcher 的配置文件？环境变量？还是接一个 secrets manager？Daemon 拉起进程时密钥怎么注入——直接写环境变量（进程的 `/proc/pid/environ` 可被同机其他进程读到）？有没有更安全的方式？

**多租户隔离。** 不同 workspace 的任务派发到同一台开发机时，进程间的隔离怎么做——Docker 容器？chroot？还是只是不同的工作目录？liskin 的 Sandbox 路径白名单在多租户场景下怎么配——按 workspace 分配不同的可访问路径？

**许可证合规。** Multica 的 NOASSERTION 许可证在阶段一启动前必须确认，这是所有后续 Dispatcher 设计文档的前置条件。如果法务不放行，所有 Dispatcher 相关设计文档的备选方案（完全自研）需要立刻启动评估。

---

这七份文档的依赖关系大致是：**Arkhiv 设计文档** 和 **liskin Provider 设计文档** 可以并行启动（阶段一、二各自的前置）；**Dispatcher Fork 设计文档** 依赖许可证合规确认和 liskin Provider 的通信契约定义；**Gate 设计文档** 依赖 Dispatcher API facade 的接口设计；**Flow 设计文档** 依赖 Dispatcher 的事件 schema；**Vercel 集成设计文档** 依赖 Flow 的 GATE 节点设计和 liskin 的 MCP client 成熟度；**可观测性设计文档** 是横切的，可以在所有组件设计稳定后统一写，但 trace ID 的传递策略应该尽早定义，免得后面补。
